# native_sqlite_ios

iOS implementation of the `native_sqlite` plugin. Uses a native Swift plugin class (`NativeSqlitePlugin`) backed by iOS's system SQLite.

Files live under Application Support and are included in device backups by
default. `DatabaseConfig.directory` selects an absolute custom directory;
`DatabaseConfig.iosAppGroup` selects the entitled App Group's shared
container so an extension or widget can open the same file. These options are
mutually exclusive.

This package is automatically selected when your Flutter app runs on iOS — you do not add it to your `pubspec.yaml` directly.

---

## Features

- Full CRUD, transactions, and raw SQL via the platform channel
- WAL journal mode requested by default; one database-specific serial queue
  coordinates Flutter and native access
- Swift schema helpers generated by `native_sqlite_generator` for native-side database access

---

## Native code generation

Running `dart run native_sqlite_generator` produces Swift files in the path configured by `native_sqlite_config.yaml`:

```
UserSchema.swift                    ← column-name constants, CREATE TABLE and index SQL
UserHelper.swift                    ← typed `User` struct and CRUD/query helper
UserStatus.swift                    ← one file per Dart enum used by a model
NativeSqliteGeneratedSupport.swift  ← row decoding shared by the helpers
DatabaseManager.swift               ← opens and migrates the database exactly like DatabaseManager.dart
```

The files `import native_sqlite_ios`. Add the output folder to the Runner
target once as a **synchronized folder** (Xcode 16+: drag
`ios/Runner/Generated` into the Runner group, choose "Create folders"), so
files added or removed by later builds are picked up automatically.

Call `try DatabaseManager.shared.initialize()` before using the helpers from
native code (background tasks, extensions). If Flutter already opened the
database, the open connection is reused. Native and Dart owners are reference
counted, so each manager can close its reference without invalidating the
other. Reopening a name with different version, schema, migration, WAL, or
foreign-key settings throws instead of silently replacing the live connection.

For lower-level native SQLite work, use
`NativeSqliteManager.shared.withConnection(name:)`. The handle is valid only
inside the closure; close and delete operations wait for that closure to end.
Generated native helpers and `withConnection` are synchronous, so call them
from a background queue; debug builds reject main-thread access. Flutter
method-channel calls use Flutter's background task queue automatically.

Native callers can perform parameterized, interactive transactions on a
background queue:

```swift
try NativeSqliteManager.shared.transaction(name: "app") { txn in
    try txn.execute(
        sql: "INSERT INTO events (value) VALUES (?)",
        arguments: ["started"]
    )
    return try txn.query(sql: "SELECT * FROM events")
}
```

## Requirements

- iOS 13+. Works with both CocoaPods and Swift Package Manager.

---

## Configuration (`native_sqlite_config.yaml`)

```yaml
native_sqlite:
  ios:
    enabled: true
    output_path: 'ios/Runner/Generated'
    generate_helpers: true
```
